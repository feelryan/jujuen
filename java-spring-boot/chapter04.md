# 2. 核心觀念與心智模型 (Core Concepts & Mental Model)

## 2.1 Spring Transaction 的代理機制 (The Proxy Mechanism of Spring Transaction)

**核心概念**：Spring 的 `@Transactional` 並非魔法，而是基於 AOP（Aspect-Oriented Programming）的代理模式。當你呼叫一個被標註的方法時，你實際上是呼叫了 Spring 產生的 Proxy 物件，該物件負責開啟交易、執行你的程式碼、然後提交或回滾。

**Core Concept:** Spring's `@Transactional` is not magic; it relies on the Proxy pattern via AOP (Aspect-Oriented Programming). When you call an annotated method, you are actually calling a Proxy object generated by Spring, which is responsible for opening the transaction, executing your code, and then committing or rolling back.

**心智模型**：想像一個「攔截器（Interceptor）」包覆著你的 Service Class。
*   **外部呼叫**：經過攔截器 -> 開啟交易 -> 執行方法 -> 關閉交易。
*   **內部呼叫（Self-invocation）**：類別內部的方法互叫（`this.method()`）會**繞過**攔截器，導致交易設定失效。這是資深工程師常犯的錯誤之一。

**Mental Model:** Imagine an "Interceptor" wrapping your Service Class.
*   **External Call:** Passes through the interceptor -> Opens transaction -> Executes method -> Closes transaction.
*   **Internal Call (Self-invocation):** Calling a method within the same class (`this.method()`) **bypasses** the interceptor, causing transaction settings to be ignored. This is a common pitfall for senior engineers.

## 2.2 Persistence Context 與 N+1 問題 (Persistence Context & The N+1 Problem)

**核心概念**：Hibernate 的 `Session`（即 JPA 的 `EntityManager`）維護著一個 Persistence Context（L1 Cache）。它追蹤實體狀態的變化。然而，當你查詢一個列表（1 次查詢），接著在迴圈中存取其關聯物件（Lazy Loading），Hibernate 會為每個物件發送額外的查詢（N 次查詢），導致 `1 + N` 次資料庫往返。

**Core Concept:** Hibernate's `Session` (JPA's `EntityManager`) maintains a Persistence Context (L1 Cache). It tracks changes in entity states. However, when you query a list (1 query) and then access its associated objects in a loop (Lazy Loading), Hibernate sends an additional query for each object (N queries), resulting in `1 + N` database round-trips.

**類比**：
*   **正常查詢**：你去超市一次買齊所有食材（Join Fetch）。
*   **N+1 問題**：你先去超市拿了一張購物清單（1 次），然後針對清單上的每樣東西，分別跑一趟超市去買（N 次）。這會極度拖慢系統速度。

**Analogy:**
*   **Normal Query:** You go to the supermarket and buy all ingredients at once (Join Fetch).
*   **N+1 Problem:** You go to the supermarket to get a shopping list (1 time), and then for each item on the list, you make a separate trip to the store to buy it (N times). This drastically slows down the system.

# 3. 實務場景與系統設計視角 (Real-World & System Design View)

## 3.1 隔離層級與併發控制 (Isolation Levels & Concurrency Control)

在設計高併發系統（如搶票系統、庫存扣減）時，預設的 `ISOLATION_DEFAULT`（通常是資料庫預設值，如 Read Committed）可能不足。

When designing high-concurrency systems (e.g., ticket booking, inventory deduction), the default `ISOLATION_DEFAULT` (usually the DB default, like Read Committed) might be insufficient.

*   **Read Committed**：防止髒讀，但可能發生不可重複讀。適用於大多數一般業務。
*   **Repeatable Read**：防止髒讀與不可重複讀，但可能發生幻讀（Phantom Read）。MySQL InnoDB 透過 MVCC 與 Next-Key Lock 在此層級解決了大部分幻讀問題。
*   **Serializable**：最強隔離，但效能最差，極少在 Production 使用。

*   **Read Committed:** Prevents Dirty Read but allows Non-repeatable Read. Suitable for most general business logic.
*   **Repeatable Read:** Prevents Dirty Read and Non-repeatable Read but allows Phantom Read. MySQL InnoDB solves most Phantom Read issues at this level using MVCC and Next-Key Locks.
*   **Serializable:** Strongest isolation but worst performance; rarely used in Production.

**設計決策**：比起提升隔離層級（會導致鎖競爭增加），實務上更常使用 **樂觀鎖（Optimistic Locking, `@Version`）** 來處理併發更新，或使用 **悲觀鎖（Pessimistic Locking, `SELECT FOR UPDATE`）** 來確保關鍵數據（如帳戶餘額）的絕對一致性。

**Design Decision:** Instead of raising the isolation level (which increases lock contention), it is more common in practice to use **Optimistic Locking (`@Version`)** for concurrent updates, or **Pessimistic Locking (`SELECT FOR UPDATE`)** to ensure absolute consistency for critical data (like account balances).

## 3.2 Connection Pool 設定 (Connection Pool Configuration)

HikariCP 是 Spring Boot 2.x+ 的預設連線池。錯誤的設定會導致系統在高負載下崩潰。

HikariCP is the default connection pool in Spring Boot 2.x+. Incorrect configuration can cause system crashes under high load.

*   **Pool Size**：不是越大越好。過大會導致 CPU 在 Context Switching 上耗費過多資源。
    *   **公式**：`connections = ((core_count * 2) + effective_spindle_count)`。對於 4 核心 CPU，設定 10-20 個連線通常已足夠處理極高吞吐量。
*   **Connection Timeout**：等待連線的超時時間。設定過長會導致請求堆積，設定過短會頻繁拋出 Exception。

*   **Pool Size:** Bigger is not always better. Too large causes excessive CPU context switching.
    *   **Formula:** `connections = ((core_count * 2) + effective_spindle_count)`. For a 4-core CPU, setting 10-20 connections is usually enough to handle very high throughput.
*   **Connection Timeout:** The timeout for waiting for a connection. Too long causes request pile-up; too short causes frequent Exceptions.

# 4. 逐步示例 (Walkthrough / Example)

## 4.1 解決 N+1 問題 (Solving the N+1 Problem)

**場景**：我們有一個部落格系統，需要顯示所有 `Post` 及其對應的 `Comment`。
**Scenario:** We have a blog system and need to display all `Posts` and their corresponding `Comments`.

### Naive Approach (The Problem)

```java
@Entity
public class Post {
    @Id
    private Long id;
    private String title;

    // Default fetch type for OneToMany is LAZY
    @OneToMany(mappedBy = "post")
    private List<Comment> comments;
}

// Service Layer
@Transactional(readOnly = true)
public List<PostDTO> getAllPosts() {
    List<Post> posts = postRepository.findAll(); // Query 1: SELECT * FROM post
    
    return posts.stream().map(post -> {
        // This triggers a separate query for each post's comments
        // Query N: SELECT * FROM comment WHERE post_id = ?
        return new PostDTO(post.getTitle(), post.getComments().size());
    }).collect(Collectors.toList());
}
```

**分析**：如果資料庫有 100 篇文章，這段程式碼會執行 101 次 SQL 查詢。
**Analysis:** If there are 100 posts in the database, this code will execute 101 SQL queries.

### Solution 1: JPQL `JOIN FETCH`

這是最常見且有效的解法。
This is the most common and effective solution.

```java
public interface PostRepository extends JpaRepository<Post, Long> {
    
    @Query("SELECT p FROM Post p LEFT JOIN FETCH p.comments")
    List<Post> findAllWithComments();
}
```

**原理**：強制 Hibernate 產生一個 SQL JOIN 語句，一次把 Post 和 Comment 撈出來。
**Mechanism:** Forces Hibernate to generate a single SQL JOIN statement, fetching both Post and Comment at once.

### Solution 2: Entity Graph (JPA 2.1+)

如果你不想寫 JPQL，可以使用 `EntityGraph`。
If you prefer not to write JPQL, you can use `EntityGraph`.

```java
public interface PostRepository extends JpaRepository<Post, Long> {
    
    @EntityGraph(attributePaths = {"comments"})
    List<Post> findAll();
}
```

### Solution 3: Hibernate `@BatchSize`

如果無法使用 JOIN（例如資料量過大導致 Cartesian Product 爆炸），可以使用 Batch Fetching。
If JOIN is not feasible (e.g., data volume is too large causing a Cartesian Product explosion), use Batch Fetching.

```java
@Entity
public class Post {
    // ...
    @OneToMany(mappedBy = "post")
    @BatchSize(size = 20) // Fetch 20 collections at a time
    private List<Comment> comments;
}
```

**效果**：Hibernate 會將 N 次查詢合併為 `N / BatchSize` 次查詢（使用 `WHERE post_id IN (?, ?, ...)`）。
**Effect:** Hibernate merges N queries into `N / BatchSize` queries (using `WHERE post_id IN (?, ?, ...)`).

# 5. 常見錯誤與反模式 (Common Pitfalls & Anti-patterns)

## 5.1 Open Session In View (OSIV)

**錯誤描述**：Spring Boot 預設開啟 `spring.jpa.open-in-view=true`。這讓 `Session` 在整個 HTTP Request 期間都保持開啟，允許在 View 層（如 Controller 或 Template）延遲加載資料。

**Description:** Spring Boot enables `spring.jpa.open-in-view=true` by default. This keeps the `Session` open for the entire duration of the HTTP Request, allowing lazy loading in the View layer (e.g., Controller or Template).

**為何不好**：
1.  **資料庫連線佔用**：連線會一直被佔用直到 HTTP 回應寫入完成，這在高延遲網路環境下會迅速耗盡 Connection Pool。
2.  **隱性查詢**：在 Controller 層不小心觸發 N+1 查詢，難以追蹤。

**Why it's bad:**
1.  **Database Connection Holding:** The connection is held until the HTTP response is fully written, which can quickly exhaust the Connection Pool in high-latency network environments.
2.  **Implicit Queries:** Accidentally triggering N+1 queries in the Controller layer makes them hard to track.

**最佳實務**：在 `application.properties` 中設定 `spring.jpa.open-in-view=false`，並強迫在 Service 層完成所有資料組裝（DTO Pattern）。

**Best Practice:** Set `spring.jpa.open-in-view=false` in `application.properties` and force all data assembly to be completed in the Service layer (DTO Pattern).

## 5.2 誤用 `Propagation.REQUIRES_NEW` (Misusing `Propagation.REQUIRES_NEW`)

**錯誤描述**：為了讓某段邏輯（如寫入 Log）不影響主交易，開發者常使用 `REQUIRES_NEW`。

**Description:** Developers often use `REQUIRES_NEW` to ensure a piece of logic (like writing logs) doesn't affect the main transaction.

**風險**：
1.  **連線池耗盡**：主交易掛起（Suspend）並佔用一個連線，新交易開啟並佔用第二個連線。如果 Pool Size 小於 `2 * Concurrent_Requests`，會發生 Deadlock（所有執行緒都在等第二個連線）。
2.  **鎖競爭**：若兩交易操作同一張表，容易發生資料庫層級的 Deadlock。

**Risk:**
1.  **Pool Exhaustion:** The main transaction is suspended (holding one connection), and the new transaction opens (holding a second connection). If Pool Size is less than `2 * Concurrent_Requests`, a Deadlock occurs (all threads waiting for a second connection).
2.  **Lock Contention:** If both transactions operate on the same table, database-level Deadlocks are likely.

# 6. 面試與實務問答切入點 (Interview & Discussion Hooks)

## Q1: 解釋 `@Transactional` 的失效場景與原因。
**Explain scenarios where `@Transactional` fails and why.**

*   **回答要點**：
    *   **Self-invocation**：類別內部方法互叫，繞過 Proxy。
    *   **Access Modifier**：方法非 `public`（依賴於代理實作，CGLIB 雖可支援但通常不建議）。
    *   **Exception Type**：預設只對 `RuntimeException` 和 `Error` 回滾，Checked Exception 需要明確指定 `rollbackFor`。
    *   **Try-Catch**：在方法內部吞掉了 Exception，Proxy 捕捉不到異常訊號。

*   **Key Points:**
    *   **Self-invocation:** Internal method calls bypass the Proxy.
    *   **Access Modifier:** Method is not `public` (depends on proxy implementation; CGLIB can support it but it's generally discouraged).
    *   **Exception Type:** Defaults to rollback only on `RuntimeException` and `Error`. Checked Exceptions need explicit `rollbackFor`.
    *   **Try-Catch:** Swallowing the Exception inside the method prevents the Proxy from catching the signal.

## Q2: 如何在不修改程式碼邏輯的情況下，監控並發現 Production 環境的 N+1 問題？
**How do you monitor and detect N+1 problems in Production without changing code logic?**

*   **回答要點**：
    *   **Hibernate Statistics**：開啟 `hibernate.generate_statistics=true`，觀察 Log 中的 Query Count 與 Fetch Count。
    *   **Datasource Proxy**：使用如 `p6spy` 或 `datasource-proxy` 來攔截並紀錄 SQL 執行次數。
    *   **APM Tools**：使用 New Relic, Datadog 或 Pinpoint，查看 Transaction Trace 中的 Database Calls 數量。

*   **Key Points:**
    *   **Hibernate Statistics:** Enable `hibernate.generate_statistics=true` and observe Query Count vs. Fetch Count in logs.
    *   **Datasource Proxy:** Use tools like `p6spy` or `datasource-proxy` to intercept and log SQL execution counts.
    *   **APM Tools:** Use New Relic, Datadog, or Pinpoint to check the number of Database Calls in Transaction Traces.

## Q3: 什麼是 Dirty Checking？它對效能有什麼影響？
**What is Dirty Checking? How does it impact performance?**

*   **回答要點**：
    *   Hibernate 在交易結束（Flush）時，會比對實體當前狀態與載入時的快照（Snapshot）。
    *   若有差異，自動產生 UPDATE 語句。
    *   **效能影響**：若是讀取大量資料（如報表），Dirty Checking 會消耗大量記憶體與 CPU。
    *   **優化**：對唯讀交易使用 `@Transactional(readOnly = true)`，Hibernate 會略過 Dirty Checking 機制，提升效能。

*   **Key Points:**
    *   Hibernate compares the entity's current state with the loaded snapshot at the end of the transaction (Flush).
    *   If differences exist, it automatically generates UPDATE statements.
    *   **Performance Impact:** For large data reads (e.g., reports), Dirty Checking consumes significant memory and CPU.
    *   **Optimization:** Use `@Transactional(readOnly = true)` for read-only transactions; Hibernate skips the Dirty Checking mechanism, improving performance.

# 7. 小結與後續延伸 (Summary & Next Steps)

## 重點回顧 (Key Takeaways)

1.  **Proxy Awareness**：始終記住 `@Transactional` 是透過 Proxy 運作的，避免 Self-invocation。
2.  **Kill N+1**：使用 `JOIN FETCH`、`EntityGraph` 或 `@BatchSize` 解決 N+1 問題，這是 ORM 效能優化的第一步。
3.  **Connection Pool Sizing**：HikariCP 的大小應根據 CPU 核心數計算，而非盲目調大。
4.  **Disable OSIV**：在大型系統中關閉 `Open Session In View`，防止連線資源耗盡。
5.  **ReadOnly Optimization**：善用 `@Transactional(readOnly = true)` 來避免不必要的 Dirty Checking。

1.  **Proxy Awareness:** Always remember `@Transactional` works via Proxy; avoid Self-invocation.
2.  **Kill N+1:** Use `JOIN FETCH`, `EntityGraph`, or `@BatchSize` to solve N+1 problems; this is the first step in ORM optimization.
3.  **Connection Pool Sizing:** HikariCP size should be calculated based on CPU cores, not blindly increased.
4.  **Disable OSIV:** Disable `Open Session In View` in large systems to prevent connection resource exhaustion.
5.  **ReadOnly Optimization:** Utilize `@Transactional(readOnly = true)` to avoid unnecessary Dirty Checking.
