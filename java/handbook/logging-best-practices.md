# 日誌框架整合與最佳實踐 / Logging Frameworks and Best Practices

## Mental model｜心智模型

在現代分散式系統中，日誌不再只是用來除錯的 `System.out.println`，它是應用程式的「心跳」與「行車紀錄器」。將日誌視為**持續產生的事件流 (Event Stream)**，這些事件最終會被收集、解析並用於監控與排查問題。
In modern distributed systems, logging is no longer just `System.out.println` for debugging; it is the "heartbeat" and "dashcam" of your application. Treat logs as a **continuous event stream**. These events are ultimately collected, parsed, and used for monitoring and troubleshooting.

要掌握 Java 日誌生態系，你需要理解以下核心架構分離：
To master the Java logging ecosystem, you must understand the following architectural separation:

1. **日誌門面 (Logging Facade)**：如 SLF4J。它是一組標準 API，就像是汽車儀表板上的按鈕。你的應用程式與第三方函式庫**只應該**依賴門面。
   **Logging Facade**: Such as SLF4J. It is a set of standard APIs, like the buttons on a car's dashboard. Your application and third-party libraries should **only** depend on the facade.
2. **日誌實作 (Logging Implementation)**：如 Logback 或 Log4j2。它是實際將日誌寫入檔案、控制台或網路的底層引擎。這應該只在應用程式的執行時期 (Runtime) 被引入。
   **Logging Implementation**: Such as Logback or Log4j2. It is the underlying engine that actually writes logs to files, consoles, or the network. This should only be introduced at the application's runtime.
3. **橋接器 (Bridges)**：用來攔截舊版框架（如 `java.util.logging`, `log4j 1.x`）的日誌，並將其重定向到 SLF4J，確保全域日誌統一。
   **Bridges**: Used to intercept logs from legacy frameworks (like `java.util.logging`, `log4j 1.x`) and redirect them to SLF4J, ensuring global log unification.

## Patterns & best practices｜常見模式與最佳實務

### 1. 結構化與 JSON 日誌 / Structured and JSON Logging
在生產環境中，放棄傳統的純文字拼接日誌，改用 JSON 格式輸出。這樣 ELK (Elasticsearch, Logstash, Kibana) 或 Datadog 等日誌聚合工具就不需要複雜的 Grok 正規表達式來解析日誌。
In production environments, abandon traditional plain-text concatenated logs and output in JSON format instead. This way, log aggregation tools like ELK or Datadog don't need complex Grok regular expressions to parse the logs.

### 2. 使用 MDC 注入上下文 / Injecting Context with MDC (Mapped Diagnostic Context)
在處理請求的入口處（如 Filter 或 Interceptor），將 `traceId`、`userId` 或 `tenantId` 放入 MDC 中。這些資訊會自動附加到該執行緒產生的每一行日誌中，這是跨微服務追蹤的基石。
At the entry point of a request (like a Filter or Interceptor), put `traceId`, `userId`, or `tenantId` into the MDC. This information will be automatically appended to every log line generated by that thread, which is the cornerstone of cross-microservice tracing.

### 3. 參數化日誌 / Parameterized Logging
永遠使用 `{}` 佔位符，而不是字串拼接。這能避免在日誌級別未啟用時，白白浪費 CPU 與記憶體去執行字串串接與物件的 `toString()`。
Always use `{}` placeholders instead of string concatenation. This prevents wasting CPU and memory on string concatenation and object `toString()` execution when the log level is disabled.
```java
// Good
log.debug("Processing user order: {}", orderId);
// Bad (Avoid)
log.debug("Processing user order: " + orderId);
```

### 4. 非同步日誌優化 / Asynchronous Logging Optimization
同步寫入磁碟會阻塞應用程式的執行緒。對於高吞吐量的系統，應啟用非同步日誌。Log4j2 基於 LMAX Disruptor 的非同步日誌效能通常優於 Logback 的 `AsyncAppender`。
Synchronous disk writing blocks application threads. For high-throughput systems, enable asynchronous logging. Log4j2's asynchronous logging, based on the LMAX Disruptor, generally outperforms Logback's `AsyncAppender`.

## Anti-patterns & pitfalls｜反模式與踩雷點

### 1. 吞噬異常堆疊 / Swallowing Exception Stack Traces
**Pitfall**: 記錄異常時，只印出 `e.getMessage()`，導致遺失最關鍵的 Stack Trace。
**Pitfall**: When logging an exception, only printing `e.getMessage()`, which results in losing the crucial Stack Trace.
```java
// ❌ Anti-pattern: 遺失 Stack Trace / Loses Stack Trace
log.error("Failed to process payment: {}", e.getMessage());
log.error("Failed to process payment", e.getMessage()); // 參數錯誤 / Wrong parameter

// ✅ Best Practice: 將 Exception 作為最後一個參數傳入 / Pass Exception as the last argument
log.error("Failed to process payment for user: {}", userId, e);
```

### 2. MDC 記憶體洩漏與上下文混亂 / MDC Memory Leaks and Context Confusion
**Pitfall**: 在 Thread Pool 環境下，執行緒會被重複使用。如果在請求結束時沒有呼叫 `MDC.clear()`，下一個使用該執行緒的請求會印出上一個請求的 `traceId`。
**Pitfall**: In a Thread Pool environment, threads are reused. If `MDC.clear()` is not called at the end of a request, the next request using that thread will print the `traceId` of the previous request.

### 3. 依賴具體的實作 API / Depending on Concrete Implementation APIs
**Pitfall**: 在業務程式碼中直接 `import org.apache.log4j.Logger` 或 `import ch.qos.logback.classic.Logger`。這會導致未來若要切換日誌底層框架時，必須修改大量業務程式碼。
**Pitfall**: Directly `import org.apache.log4j.Logger` or `import ch.qos.logback.classic.Logger` in business code. This forces you to modify a massive amount of business code if you ever need to switch the underlying logging framework.

### 4. 記錄敏感資訊 (PII) / Logging Sensitive Information (PII)
**Pitfall**: 不小心將使用者的密碼、信用卡號或身分證字號印在日誌中。這違反了 GDPR 等隱私法規。應在日誌框架層級設定 Masking (遮罩) 規則，或避免將敏感物件直接傳入日誌。
**Pitfall**: Accidentally printing user passwords, credit card numbers, or SSNs in logs. This violates privacy regulations like GDPR. You should configure masking rules at the logging framework level or avoid passing sensitive objects directly to logs.

## Checklists & workflows｜檢查清單與流程

- [ ] **Facade Check**: 我已經確認專案的 `pom.xml` / `build.gradle` 中，業務模組只依賴 `slf4j-api`，而實作（如 `logback-classic`）僅在最終的啟動模組宣告為 `runtimeOnly`。 / I have verified that business modules only depend on `slf4j-api`, and the implementation is declared as `runtimeOnly` in the final application module.
- [ ] **Bridge Configuration**: 我已經引入了必要的橋接器（如 `log4j-over-slf4j`, `jcl-over-slf4j`），並排除了第三方套件自帶的日誌實作，確保所有日誌都流向 SLF4J。 / I have included necessary bridges and excluded logging implementations brought by third-party libraries to ensure all logs flow to SLF4J.
- [ ] **MDC Cleanup**: 我已經確保在 Servlet Filter, Spring Interceptor 或 AOP 的 `finally` 區塊中執行了 `MDC.clear()`。 / I have ensured `MDC.clear()` is executed in the `finally` block of my Servlet Filter, Spring Interceptor, or AOP.
- [ ] **Async Enabled**: 在效能敏感的生產環境中，我已經配置了非同步日誌（AsyncAppender 或 Log4j2 AsyncLogger）。 / In performance-sensitive production environments, I have configured asynchronous logging.
- [ ] **Exception Logging**: 我已經檢查程式碼庫，確保 `log.error` 都有正確傳遞 Exception 物件本身，而不是只傳字串。 / I have audited the codebase to ensure `log.error` properly passes the Exception object itself, not just a string.

## Real-world examples｜實戰案例

### 案例 1：正確管理 MDC 的生命週期 / Managing MDC Lifecycle Correctly

在 Web 應用中，我們通常使用 Filter 來攔截請求並注入追蹤 ID。
In a web application, we typically use a Filter to intercept requests and inject a trace ID.

```java
import org.slf4j.MDC;
import javax.servlet.*;
import java.io.IOException;
import java.util.UUID;

public class RequestTracingFilter implements Filter {
    
    private static final String TRACE_ID_KEY = "traceId";

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain) 
            throws IOException, ServletException {
        try {
            // 1. 生成或從 HTTP Header 獲取 Trace ID / Generate or get Trace ID from HTTP Header
            String traceId = UUID.randomUUID().toString();
            
            // 2. 放入 MDC / Put into MDC
            MDC.put(TRACE_ID_KEY, traceId);
            
            // 3. 繼續處理請求 / Continue processing the request
            chain.doFilter(request, response);
        } finally {
            // 4. 絕對要在 finally 中清除，避免 Thread Pool 污染！
            // MUST clear in finally to avoid Thread Pool pollution!
            MDC.clear();
        }
    }
}
```

### 案例 2：Logback 非同步與 JSON 配置範例 / Logback Async and JSON Configuration Example

以下是一個實戰中常見的 `logback-spring.xml` 結構，展示如何將日誌輸出為 JSON 並使用非同步處理。
Here is a common real-world `logback-spring.xml` structure, demonstrating how to output logs as JSON and use asynchronous processing.

```xml
<configuration>
    <!-- 引入 Logstash Logback Encoder 來輸出 JSON -->
    <!-- Include Logstash Logback Encoder to output JSON -->
    <appender name="JSON_CONSOLE" class="ch.qos.logback.core.ConsoleAppender">
        <encoder class="net.logstash.logback.encoder.LogstashEncoder">
            <!-- 自動包含 MDC 中的變數 -->
            <!-- Automatically include variables from MDC -->
            <includeMdc>true</includeMdc>
        </encoder>
    </appender>

    <!-- 非同步 Appender 包裝器 / Async Appender Wrapper -->
    <appender name="ASYNC_JSON_CONSOLE" class="ch.qos.logback.classic.AsyncAppender">
        <!-- 佇列大小 / Queue size -->
        <queueSize>512</queueSize>
        <!-- 佇列滿時不丟棄 INFO 級別以上的日誌 / Do not drop logs INFO and above when queue is full -->
        <discardingThreshold>0</discardingThreshold>
        <appender-ref ref="JSON_CONSOLE" />
    </appender>

    <!-- 生產環境使用非同步 JSON / Use Async JSON in Production -->
    <springProfile name="prod">
        <root level="INFO">
            <appender-ref ref="ASYNC_JSON_CONSOLE" />
        </root>
    </springProfile>
</configuration>
```

### 案例 3：跨執行緒傳遞 MDC / Passing MDC Across Threads

當使用 `CompletableFuture` 或自訂執行緒池時，MDC 不會自動傳遞到子執行緒。你需要手動複製上下文。
When using `CompletableFuture` or custom thread pools, MDC is not automatically passed to child threads. You need to manually copy the context.

```java
// 1. 在主執行緒獲取當前的 MDC Context / Get current MDC context in main thread
Map<String, String> contextMap = MDC.getCopyOfContextMap();

CompletableFuture.runAsync(() -> {
    // 2. 在子執行緒中設定 MDC / Set MDC in child thread
    if (contextMap != null) {
        MDC.setContextMap(contextMap);
    }
    try {
        log.info("This log will have the correct traceId");
    } finally {
        // 3. 執行緒池用完後清理 / Clean up after thread pool usage
        MDC.clear();
    }
});
```
*(註：實務上通常會實作一個自訂的 `TaskDecorator` 或包裝過的 `Executor` 來自動處理這段邏輯。 / Note: In practice, a custom `TaskDecorator` or a wrapped `Executor` is usually implemented to handle this logic automatically.)*
