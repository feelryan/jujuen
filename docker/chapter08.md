# 2. 核心觀念與心智模型 (Core Concepts & Mental Model)

## 2.1 日誌即串流 (Logs as Event Streams)

**心智模型：** 不要將日誌視為「檔案」，應視為「串流（Stream）」。
**Mental Model:** Do not view logs as "files," but as "streams."

在傳統 VM 部署中，應用程式通常負責將日誌寫入特定檔案並進行輪替（Log Rotation）。在 Docker（以及 Cloud Native）哲學中，應用程式應將日誌視為事件串流，直接寫入 `stdout` 和 `stderr`。Docker Daemon 就像一個「攔截器」，捕捉這些串流並透過 **Logging Driver** 轉發到目的地（檔案、Syslog 或日誌聚合系統）。

In traditional VM deployments, applications are often responsible for writing logs to specific files and handling rotation. In the Docker (and Cloud Native) philosophy, applications should treat logs as event streams, writing directly to `stdout` and `stderr`. The Docker Daemon acts as an "interceptor," capturing these streams and forwarding them via a **Logging Driver** to a destination (file, Syslog, or log aggregation system).

## 2.2 PID 1 與信號傳遞 (PID 1 and Signal Propagation)

**心智模型：** 容器內的 PID 1 是該命名空間（Namespace）的「init 進程」。
**Mental Model:** PID 1 inside a container is the "init process" for that namespace.

Linux 核心對 PID 1 有特殊處理：它負責清理孤兒進程（Orphaned Processes）並處理信號（Signals）。如果你的應用程式（例如 Java 或 Python script）直接作為 PID 1 執行，且沒有正確處理 `SIGTERM` 或 `SIGINT`，容器將無法優雅關閉（Graceful Shutdown），甚至產生大量殭屍進程耗盡資源。

The Linux kernel treats PID 1 specially: it is responsible for reaping orphaned processes and handling signals. If your application (e.g., a Java or Python script) runs directly as PID 1 and does not correctly handle `SIGTERM` or `SIGINT`, the container will fail to shut down gracefully and may even generate a large number of zombie processes, exhausting resources.

## 2.3 容器網路命名空間 (Container Network Namespaces)

**正規定義：** 每個容器（預設情況下）擁有獨立的 Network Namespace，包含自己的 IP、路由表與 iptables 規則。
**Formal Definition:** Each container (by default) possesses an isolated Network Namespace, containing its own IP, routing table, and iptables rules.

除錯時，不能只在 Host 上看 `ifconfig`。你需要「進入」該 Namespace 視角。這與 VM 的網路除錯類似，但工具鏈（如 `docker exec`, `nsenter`）不同。

When debugging, looking at `ifconfig` on the Host is insufficient. You need to "enter" the perspective of that Namespace. This is similar to VM network debugging, but the toolchain (e.g., `docker exec`, `nsenter`) is different.

# 3. 實務場景與系統設計視角 (Real-World & System Design View)

## 3.1 生產環境日誌架構 (Production Logging Architecture)

在系統設計面試或實務架構中，單機的 `docker logs` 指令是不可擴展的。

In system design interviews or practical architecture, the single-host `docker logs` command is not scalable.

*   **典型架構 (Typical Architecture):**
    *   **App:** 寫入 `stdout`/`stderr`（不關心日誌去向）。
    *   **Docker Daemon:** 配置 `json-file` (附帶 rotation) 作為緩衝，或直接使用 `fluentd`/`splunk` driver。
    *   **Log Shipper:** 通常會在每個 Node 部署一個 Agent (如 Fluent Bit, Filebeat) 讀取 Docker 產生的 json-file，並發送到 Elasticsearch/S3/Datadog。
    *   **Trade-off:** 直接使用 Docker 的 `fluentd` driver 雖然方便，但若日誌後端當機，可能會導致容器阻塞（Blocking mode）或日誌遺失（Non-blocking mode）。因此，**"Log to file (with rotation) + Sidecar/DaemonSet Shipper"** 通常是較穩健的選擇。

    *   **App:** Writes to `stdout`/`stderr` (agnostic of log destination).
    *   **Docker Daemon:** Configured with `json-file` (with rotation) as a buffer, or directly using `fluentd`/`splunk` drivers.
    *   **Log Shipper:** Typically, an Agent (e.g., Fluent Bit, Filebeat) is deployed on each Node to read the json-files generated by Docker and ship them to Elasticsearch/S3/Datadog.
    *   **Trade-off:** While using Docker's `fluentd` driver directly is convenient, if the log backend goes down, it can cause container blocking (Blocking mode) or log loss (Non-blocking mode). Therefore, **"Log to file (with rotation) + Sidecar/DaemonSet Shipper"** is usually the more robust choice.

## 3.2 健康檢查與負載平衡 (Health Checks & Load Balancing)

在微服務架構中，Load Balancer (LB) 需要知道何時停止發送流量。

In a microservices architecture, the Load Balancer (LB) needs to know when to stop sending traffic.

*   **Docker Healthcheck:** 定義在 `Dockerfile` 或 `docker-compose.yml` 中。
*   **Auto-healing:** 當狀態變為 `unhealthy`，編排工具（如 Docker Swarm 或 K8s）可以重啟容器。
*   **設計考量:** Health check 檢查必須「輕量」且「準確」。檢查 DB 連線是常見做法，但若 DB 變慢導致所有微服務同時判定 unhealthy 並重啟，會造成 **Thundering Herd (驚群效應)**。

*   **Docker Healthcheck:** Defined in `Dockerfile` or `docker-compose.yml`.
*   **Auto-healing:** When status becomes `unhealthy`, orchestration tools (like Docker Swarm or K8s) can restart the container.
*   **Design Considerations:** Health checks must be "lightweight" and "accurate." Checking DB connectivity is common, but if the DB slows down causing all microservices to judge themselves unhealthy and restart simultaneously, it creates a **Thundering Herd** effect.

# 4. 逐步示例 (Walkthrough / Example)

## 4.1 配置生產級日誌 (Configuring Production-Grade Logging)

預設的 Docker 設定是不安全的，因為 `json-file` 沒有大小限制，可能填滿 Host 硬碟。

The default Docker configuration is unsafe because `json-file` has no size limit and can fill up the Host disk.

### 步驟 1: 設定 Daemon 全域預設值 (Step 1: Set Daemon Global Defaults)

修改 `/etc/docker/daemon.json` 以確保所有新建容器都有日誌輪替。

Modify `/etc/docker/daemon.json` to ensure all newly created containers have log rotation.

```json
{
  "log-driver": "json-file",
  "log-opts": {
    "max-size": "10m",
    "max-file": "3"
  }
}
```

### 步驟 2: 針對特定容器使用 Non-blocking 模式 (Step 2: Use Non-blocking Mode for Specific Containers)

如果我們決定使用 `fluentd` driver 直接發送日誌，必須防止日誌系統變慢時拖垮應用程式。

If we decide to use the `fluentd` driver to ship logs directly, we must prevent the application from crashing if the logging system slows down.

```bash
docker run -d \
  --log-driver=fluentd \
  --log-opt fluentd-address=localhost:24224 \
  --log-opt mode=non-blocking \
  --log-opt max-buffer-size=4m \
  my-high-throughput-app
```

*   **Why:** 預設是 `blocking`。若 Fluentd 無回應，`stdout` write 操作會 block 住，導致 App 停止回應。
*   **Trade-off:** `non-blocking` 模式下，若 buffer 滿了，最舊的日誌會被丟棄（Log Loss），但保住了服務可用性（Availability）。

*   **Why:** Default is `blocking`. If Fluentd is unresponsive, `stdout` write operations will block, causing the App to hang.
*   **Trade-off:** In `non-blocking` mode, if the buffer fills up, the oldest logs are dropped (Log Loss), but service availability is preserved.

## 4.2 解決 Zombie Processes 問題 (Solving the Zombie Processes Problem)

### 問題背景 (Scenario)
你寫了一個 Python script 啟動外部 subprocess，但發現容器運行一段時間後，記憶體未釋放，且 `docker exec` 進去看到大量 `[python] <defunct>` 進程。

You wrote a Python script that starts external subprocesses, but found that after the container ran for a while, memory wasn't released, and `docker exec` showed a large number of `[python] <defunct>` processes.

### 解決方案 (Solution)

**方法 A: 使用 `--init` 旗標 (Method A: Use `--init` flag)**
Docker 內建了 `tini` (tiny init)，可以作為 PID 1 幫你轉發信號並回收殭屍進程。

Docker has `tini` (tiny init) built-in, which can act as PID 1 to forward signals and reap zombie processes for you.

```bash
docker run --init -d my-python-app
```

**方法 B: 在 Dockerfile 中整合 Tini (Method B: Integrate Tini in Dockerfile)**
這在 Kubernetes 等不一定支援 `--init` 參數的環境中更通用。

This is more universal in environments like Kubernetes that may not support the `--init` parameter.

```dockerfile
# Dockerfile
FROM python:3.9-slim

# Install tini
ENV TINI_VERSION v0.19.0
ADD https://github.com/krallin/tini/releases/download/${TINI_VERSION}/tini /tini
RUN chmod +x /tini

ENTRYPOINT ["/tini", "--"]
CMD ["python", "app.py"]
```

## 4.3 使用 `nsenter` 排查網路 (Network Troubleshooting with `nsenter`)

當容器內沒有 `ping`, `curl`, `ip` 等工具（例如 Distroless image），如何除錯？

How do you debug when the container lacks tools like `ping`, `curl`, or `ip` (e.g., Distroless images)?

1.  **獲取容器 PID (Get Container PID):**
    ```bash
    PID=$(docker inspect -f '{{.State.Pid}}' <container_id>)
    ```

2.  **使用 `nsenter` 進入網路命名空間 (Use `nsenter` to enter Network Namespace):**
    這會使用 Host 上的工具（ping, curl），但在容器的網路環境中執行。
    This uses tools from the Host (ping, curl) but executes them within the container's network context.

    ```bash
    # -t: target PID, -n: network namespace
    sudo nsenter -t $PID -n ip addr
    sudo nsenter -t $PID -n curl -v http://google.com
    ```

# 5. 常見錯誤與反模式 (Common Pitfalls & Anti-patterns)

## 5.1 無限制的日誌增長 (Unbounded Log Growth)

*   **錯誤 (Pitfall):** 使用預設 `json-file` 且未配置 `max-size`。
*   **後果 (Consequence):** 長期運行的容器會產生數十 GB 的 JSON 檔，耗盡 Node 磁碟空間，導致 `No space left on device`，甚至影響 Host OS 穩定性。
*   **修正 (Fix):** 總是設定 Log Rotation（見 4.1 節）。

*   **Pitfall:** Using default `json-file` without configuring `max-size`.
*   **Consequence:** Long-running containers generate tens of GBs of JSON files, exhausting Node disk space, leading to `No space left on device`, and potentially affecting Host OS stability.
*   **Fix:** Always configure Log Rotation (see Section 4.1).

## 5.2 依賴 IP 位址而非 DNS (Relying on IPs instead of DNS)

*   **錯誤 (Pitfall):** 在應用程式設定檔中寫死其他容器的 IP。
*   **後果 (Consequence):** 容器重啟後 IP 會變動，導致連線失敗。
*   **修正 (Fix):** 使用 Docker User-defined Networks，透過 Container Name 或 Service Name 進行 DNS 解析。

*   **Pitfall:** Hardcoding other containers' IPs in application configuration files.
*   **Consequence:** IPs change after container restart, causing connection failures.
*   **Fix:** Use Docker User-defined Networks and rely on DNS resolution via Container Name or Service Name.

## 5.3 在 Health Check 中執行過重邏輯 (Heavy Logic in Health Checks)

*   **錯誤 (Pitfall):** Health Check script 執行完整的資料庫掃描或複雜運算。
*   **後果 (Consequence):** 消耗大量資源；當系統負載高時，Health Check 超時失敗，導致容器被錯誤地重啟，進一步加重系統負載（Death Spiral）。
*   **修正 (Fix):** 保持 Health Check 簡單（例如：檢查 `/healthz` endpoint，僅確認 DB 連線池是否可用，而非執行 Query）。

*   **Pitfall:** Health Check script performs full database scans or complex computations.
*   **Consequence:** Consumes significant resources; when system load is high, Health Checks time out and fail, causing containers to be restarted erroneously, further increasing system load (Death Spiral).
*   **Fix:** Keep Health Checks simple (e.g., check a `/healthz` endpoint that only verifies if the DB connection pool is available, rather than executing a Query).

# 6. 面試與實務問答切入點 (Interview & Discussion Hooks)

## 6.1 問題：如何處理 Docker 日誌造成的磁碟 I/O 瓶頸？
**Question: How do you handle disk I/O bottlenecks caused by Docker logs?**

*   **高分回答要點 (Key Points):**
    1.  **非同步寫入 (Async/Non-blocking):** 提及 `mode=non-blocking`，避免 App 被 I/O wait 卡住。
    2.  **避免寫入檔案系統 (Avoid FS):** 對於極高流量，考慮使用 `log-driver=none` 並讓 App 直接寫入 Socket 或透過 UDP 發送（雖然這增加了 App 複雜度，但在極端效能要求下是選項）。
    3.  **掛載專用磁碟 (Dedicated Mount):** 將 `/var/lib/docker` 掛載在獨立的高速磁碟，避免影響 OS 操作。
    4.  **取樣 (Sampling):** 在 App 層級做日誌等級過濾（Level Filtering）或取樣，減少垃圾日誌。

## 6.2 問題：為什麼 `docker stop` 有時需要等 10 秒才結束？
**Question: Why does `docker stop` sometimes take 10 seconds to finish?**

*   **高分回答要點 (Key Points):**
    1.  **SIGTERM vs SIGKILL:** 解釋 `docker stop` 先發送 `SIGTERM`，等待 grace period（預設 10s），若進程未退出則發送 `SIGKILL`。
    2.  **信號遮蔽 (Signal Masking):** 說明 Shell form (`CMD "python app.py"`) 會啟動 `sh` 作為 PID 1，而 `sh` 不會轉發信號給子進程。
    3.  **Exec form:** 強調應使用 Exec form (`CMD ["python", "app.py"]`) 或 Tini (`--init`) 來確保信號正確接收與處理。

## 6.3 問題：如何在不安裝工具的情況下，除錯 Distroless 容器的網路？
**Question: How do you debug networking in a Distroless container without installing tools?**

*   **高分回答要點 (Key Points):**
    1.  **Sidecar Container:** 啟動一個帶有工具的容器（如 `nicolaka/netshoot`），加入目標容器的 Network Namespace (`--network container:<target_id>`)。
    2.  **nsenter:** 在 Host 上使用 `nsenter` 進入目標 PID 的 namespace。
    3.  **Ephemeral Containers:** (若延伸到 K8s) 提及 `kubectl debug` 的 ephemeral container 概念。

# 7. 小結與後續延伸 (Summary & Next Steps)

## 小結 (Summary)
1.  **Logs are Streams:** 應用程式只管寫 `stdout/stderr`，由 Docker Daemon 透過 Drivers 處理路由。
2.  **Rotation is Mandatory:** 永遠為 `json-file` 設定 `max-size` 與 `max-file`。
3.  **PID 1 Matters:** 使用 `exec` 格式或 `tini` (`--init`) 來避免殭屍進程並確保 Graceful Shutdown。
4.  **Health Checks:** 區分 Liveness（存活）與 Readiness（就緒），避免驚群效應。
5.  **Namespace Debugging:** 善用 `nsenter` 或 `--network container:xxx` 進行深層除錯。
